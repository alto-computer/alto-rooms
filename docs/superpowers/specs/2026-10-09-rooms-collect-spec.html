rooms-collect — 아무것도 안 해도 모이는 수집기

Spec · 2026-10-09author: jun-hash선행: v1-spec, v2-ask-spec §12 (sources.json), plugin-tools-spec참고: Orca session search

사용자가 CLAUDE.md, 훅, 스킬 습관에 기대지 않아도 에이전트가 쓴 HTML이 Rooms에 들어온다. 수집과 검색은 별도 프로세스 rooms-collect가 맡고, 코어(roomsd)는 지금처럼 폴더만 읽는다.

0. 개요

원칙 (사용자 결정)

에이전트 로그 형식에 대한 지식은 rooms-collect의 어댑터만 안다. 코어는 수집기를 모른다. 둘은 이미 있는 계약인 폴더 규칙으로만 이어진다. 결합은 없애지 못하지만 한곳에 가두고, 사용자 설정에서는 없앤다.

역할 분담: 과거(설치 전) 문서는 온보딩 스킬이 사용자와 대화하며 방을 정한다. 미래(설치 후) 문서는 수집기가 자동으로 모은다.

Goal

  • 설치 이후 에이전트가 쓴 .html/.htm이 사용자 행동 없이 2초 안팎으로 Rooms에 나타난다.
  • 같은 문서는 몇 번을 다시 읽어도 한 번만 들어온다. 사용자가 지운 링크는 다시 생기지 않는다.
  • 에이전트가 지우기 전에 대화 원문을 기기 안 보관소에 남긴다. 만든 문서와 그 대화를 나중에 다시 읽고 회고, 공부할 수 있게.
  • 대화 기록에 대한 전문 검색(SQLite FTS5)의 토대를 만든다. 이후 검색 UI, 분석, 학습용 보관, 기기 간 동기화가 같은 틀 위에 붙는다.
  • 가볍다. 상주 메모리는 작은 상수, 디스크는 원문을 복사하지 않는 색인 위주.

Out of scope

  • 앱 안 검색 UI. 이번에는 색인과 CLI(rooms-collect search)까지.
  • 분석 싱크, 문서 옆 대화 보기, 안 읽음 표시, 하루 회고, 기기 간 동기화용 jsonl 내보내기. 스키마와 확장 지점만 열어 둔다(§12).
  • 30일보다 오래된 대화의 검색. 원문은 보관소에 남으므로 나중에 보관소를 다시 색인하면 된다(§12).
  • 토픽 자동 분류. Rooms는 AI를 부르지 않는다. 분류는 스킬(사용자의 에이전트)의 일.
  • Claude Code, Codex, Aside 외 에이전트 어댑터. 어댑터 계약만 맞추면 이후 추가.
  • macOS 외 플랫폼.

1. 사용자 경험

첫 실행지금과 같다. 온보딩 카드가 한 줄 프롬프트를 보여 주고, 사용자는 에이전트에 붙여 넣어 방을 함께 정한다.
동시에앱이 rooms-collect를 띄운다. 이 시점이 linker.since가 된다. 백그라운드에서 검색 색인을 채운다.
이후에이전트가 HTML을 쓰면 수집기가 같은 repo 이름의 방, 없으면 inbox에 링크한다. 사용자는 아무것도 안 한다.
정리원할 때 "rooms 정리해줘"로 inbox를 방으로 옮긴다. 선택이다.

온보딩을 건너뛴 사용자도 설치 이후 문서는 자동으로 모인다. 앱이 계속 빈 상태로 남지 않는다.

2. 결정

#결정이유
D1수집은 별도 바이너리 rooms-collect. 앱(Tauri)이 roomsd와 같은 방식의 sidecar로 띄우고 끈다.코어의 "에이전트 로그를 모른다" 원칙 유지. 수집기가 죽어도 앱은 정상.
D2수집기 → 코어는 폴더로만. 링크를 만들면 roomsd가 기존 감시로 반영한다. 새 API 없음.roomsd가 꺼져 있어도 수집이 이어지고, 토큰도 필요 없다. README의 "방 폴더에 HTML을 쓰면 끝" 계약 그대로.
D3저장소는 SQLite(WAL) 하나. 이벤트와 파일 커서를 한 트랜잭션으로 커밋한다.중간에 죽어도 중복, 누락이 없다. jsonl은 "줄 추가"와 "커서 저장"이 분리돼 이를 보장하기 어렵다.
D4DB 위치는 ~/Library/Application Support/computer.alto.rooms/collect.db. ~/rooms 안에 두지 않는다.~/rooms는 Dropbox, git으로 동기화될 수 있다. 동기화 폴더의 SQLite는 깨진다.
D5DB는 버려도 되는 캐시. 원본은 에이전트 로그. 스키마 버전이 다르거나 파일이 깨지면 지우고 다시 만든다.복구 절차가 "삭제 후 재시작" 하나로 끝난다.
D6사용자 상태(링크, 지운 목록, sources.json)는 DB가 아니라 ~/rooms 안 파일에 둔다.DB를 버려도 사용자 결정이 남는다. 동기화되는 진짜 데이터는 이쪽.
D7색인(ingest)은 과거 로그까지 읽지만, 링크는 linker.since 이후 이벤트에만 한다.검색은 과거가 필요하고, 과거 문서의 방 정하기는 스킬이 사용자와 한다. 둘을 같은 이벤트 스트림의 다른 소비자로 분리.
D8FTS5는 contentless(content='')로 만든다. 원문은 복사하지 않고, 발췌는 원본 로그에서 읽는다.디스크를 가볍게. 원본 로그가 지워졌으면 보관소 사본에서 읽고, 그것도 없으면 이벤트마다 둔 짧은 미리보기(≤ 240자)를 쓴다.
D10대화 원문 보관소를 이번 범위에 넣는다. 수집기가 읽은 로그 바이트를 그대로 ~/Library/Application Support/computer.alto.rooms/archive/에 복사하고, 다 쓴 세션은 zstd로 압축한다. 기본 켬.Claude Code는 30일이 지난 로그를 지운다. 회고, 공부가 목적이면 켜는 날부터 사라지는 기록이 없어야 한다. DB(캐시)와 달리 다시 만들 수 없는 데이터라 따로 둔다.
D9스킬 v8: 습관 규칙과 CLAUDE.md 한 줄을 뺀다. 첫 정리, 재정리, "이거 방에 넣어줘"는 남긴다.자동 수집이 대신한다. 수집기가 깨졌을 때의 수동 대안은 남긴다.

4. 어댑터와 이벤트

어댑터 계약

pub trait Adapter {
    fn agent(&self) -> &'static str;                 // "claude-code", "codex", "aside"
    fn roots(&self) -> Vec<PathBuf>;                   // 감시할 로그 폴더
    fn is_log(&self, path: &Path) -> bool;              // *.jsonl 등
    /// 한 파일의 [from, to) 바이트를 읽어 이벤트로. 완결되지 않은 마지막 줄은 읽지 않고 남긴다.
    fn read(&self, file: &LogFile, from: u64, ctx: &mut FileCtx) -> Result<Batch, AdapterError>;
}
pub struct Batch { pub events: Vec<Event>, pub end_offset: u64 }   // end_offset = 마지막 완결 줄 끝
pub struct FileCtx { pub session: Option<String>, pub cwd: Option<PathBuf> }  // 파일별로 DB에 보관

FileCtx는 Codex처럼 세션 id, cwd가 앞쪽 메타 줄에만 있는 형식을 위해 파일 커서와 함께 저장한다. 이어 읽을 때 앞부분을 다시 읽지 않는다.

이벤트 (v1)

kind필드소비자
session.seenagent, session, cwd, title?, started_atfts (세션 목록)
messagerole(user|assistant), text_ref, previewfts
tool.callname, text_ref, previewfts (tool_text)
file.writtenpath(절대), op(write|edit|patch|shell), explicit(bool)linker, sources

공통 필드: id, agent, session, ts(UTC), cwd, source(로그 파일 경로, 시작 바이트, 길이). text_ref는 원문 위치 포인터이고 원문을 복사하지 않는다.

이벤트 id (중복 방지의 핵심): sha256(agent ‖ session ‖ native_id ‖ sub_index)의 앞 16바이트(hex). native_id는 로그가 주는 고유 id(Claude Code uuid, Codex 레코드 id)이고, 없으면 파일 identity ‖ 줄 시작 바이트. sub_index는 한 줄에서 나온 n번째 이벤트. 같은 줄을 몇 번 읽어도 같은 id가 나오고 PRIMARY KEY가 두 번째를 막는다.

HTML 쓰기 감지 (find_html.py v7 규칙의 Rust 이식)

  • Claude Code: type=assistant 레코드의 tool_use 중 Write, Edit, MultiEdit, NotebookEdit의 file_path가 HTML이면 explicit=true. Bash는 셸 토큰화로 리다이렉트, tee, cp/mv/install 대상만 explicit=false.
  • Codex: apply_patch의 *** Add|Update File: x.html은 explicit=true. 그 외 exec 명령은 쓰기 힌트가 있을 때만 explicit=false.
  • Codex 압축 로그: Codex는 오래된 rollout을 .jsonl.zst로 압축한다. 압축 파일은 이어 읽기 없이 통째로 읽는다(offset은 압축 해제 기준). .jsonl이 .zst로 바뀌면 새 파일로 보이지만 이벤트 id가 같아 중복되지 않는다.
  • Aside: ~/.aside/u/<계정>/sessions/<YYYY-MM-DD>_<id>/messages.jsonl. 세션 id는 폴더 이름, 시각은 epoch ms. role=assistant의 toolCall 중 repl(JS)의 writeFile과 이름에 write/edit가 들어간 도구의 path는 explicit=true, bash는 explicit=false. 문서로 보는 건 ~/.aside 안에서는 artifacts 폴더뿐(find_html.py와 같다).
  • 상대 경로는 이벤트 시점의 cwd로 절대화. 해석할 수 없으면 버린다.
  • 빠른 거르기: 줄에 .htm이 없고 메타/메시지 줄이 아니면 JSON 파싱을 하지 않는다.

회귀 방지: test_find_html.py의 픽스처를 Rust 테스트로 옮겨 두 구현의 판단이 같은지 확인한다.

5. 저장소

PRAGMA journal_mode=WAL; PRAGMA synchronous=NORMAL; PRAGMA auto_vacuum=INCREMENTAL; PRAGMA busy_timeout=5000;

CREATE TABLE meta(key TEXT PRIMARY KEY, value TEXT NOT NULL);         -- schema_version, linker_since, ...
CREATE TABLE files(                                                   -- 로그 파일별 커서
  path TEXT PRIMARY KEY, agent TEXT NOT NULL,
  dev INTEGER, ino INTEGER, size INTEGER, mtime_ms REAL,
  offset INTEGER NOT NULL DEFAULT 0,                                  -- 마지막 완결 줄 끝
  archive_path TEXT, archive_len INTEGER NOT NULL DEFAULT 0,          -- 보관 사본과 그 커밋된 길이
  ctx TEXT,                                                           -- FileCtx JSON
  state TEXT NOT NULL DEFAULT 'current',                              -- current | due | failed
  fail_count INTEGER NOT NULL DEFAULT 0, failed_mtime_ms REAL);
CREATE TABLE events(
  rowid INTEGER PRIMARY KEY AUTOINCREMENT,
  id TEXT NOT NULL UNIQUE, kind TEXT NOT NULL, agent TEXT NOT NULL, session TEXT,
  ts TEXT, cwd TEXT, path TEXT, explicit INTEGER,
  src_path TEXT NOT NULL, src_offset INTEGER NOT NULL, src_len INTEGER NOT NULL,
  preview TEXT);                                                      -- ≤ 240자
CREATE INDEX events_kind_rowid ON events(kind, rowid);
CREATE INDEX events_session ON events(agent, session);
CREATE TABLE sink_cursors(sink TEXT PRIMARY KEY, last_rowid INTEGER NOT NULL);
CREATE VIRTUAL TABLE messages_fts USING fts5(
  user_text, assistant_text, tool_text, identifiers,
  content='', contentless_delete=1,
  tokenize="unicode61 tokenchars '_.-/+'");                          -- rowid = events.rowid
  • 한 파일 처리 = 한 트랜잭션: 새 이벤트 INSERT OR IGNORE + files 커서, ctx 갱신. 커밋 전 죽으면 둘 다 없던 일.
  • 싱크는 각자 커서: events.rowid > last_rowid를 순서대로 처리하고, 처리한 만큼 커서를 올린다. 싱크 하나가 실패해도 다른 싱크와 수집은 계속된다.
  • schema_version이 다르면 DB 파일을 지우고 새로 만든다(D5). 이때 링커는 ~/rooms의 사용자 상태(§7)로 중복을 막으므로 다시 링크하지 않는다.

6. 수집 규칙

#규칙
C1깨우기: 로그 루트를 FSEvents로 감시(디바운스 100ms, roomsd의 80ms와 비슷하게)하고, 놓친 변경을 위해 60초마다 한 번 전체 stat 대조. 바뀐 파일만 읽는다.
C2읽기 결정은 (현재 stat, files 행)만의 함수다. 행 없음 → 0부터. 같은 dev/ino이고 size ≥ offset → offset부터. inode 변경 또는 size < offset → 다른 파일로 보고 0부터(이벤트 id가 같으면 무시되므로 안전). due → 0부터.
C3완결되지 않은 마지막 줄(개행 없음)은 읽지 않고 offset을 그 앞에 둔다.
C4같은 mtime에서 3번 실패한 파일은 failed로 두고 mtime이 바뀔 때까지 건너뛴다. 타이머 없이 stat이 재시도 정책이다.
C5보관 기간: 색인은 mtime이 history_days(기본 30일) 안인 로그만. 기간 밖으로 나간 파일의 이벤트와 FTS 행은 조금씩 지운다(incremental vacuum).
C6첫 색인은 최신 파일부터, 한 번에 최대 8 MiB씩 끊어 읽고 그 사이에 양보한다. 새로 쓰이는 파일이 항상 먼저 처리된다.
C7수집기는 로그 파일에 절대 쓰지 않는다. 열 때 읽기 전용.

7. 링크 싱크 (linker)

#규칙
L1대상: file.written 중 ts ≥ linker.since. linker.since는 수집기 첫 실행 시각이며 meta와 ~/rooms/.rooms/collect/state.json 양쪽에 기록한다(DB를 다시 만들어도 유지).
L2링크 전에 파일이 실제로 있는지 확인한다. 로그 줄이 파일보다 먼저 기록될 수 있으므로, 없으면 0.5초, 2초, 10초 뒤 다시 확인하고 그래도 없으면 버린다. explicit=false(셸 추정)는 추가로 이벤트 이후 mtime이 바뀐 경우에만 링크한다.
L3제외: find_html.py not_a_document와 같은 규칙(scratchpad, node_modules, ~/.claude, ~/.codex, ~/rooms/.rooms, 시스템 tmp 등), ~/rooms 안에서 쓴 파일(이미 Rooms에 있음), rooms-core::rules가 무시하는 경로.
L4이미 링크됨: ~/rooms 아래 어느 symlink든 같은 realpath를 가리키면 건너뛴다. 연결(linked) 방 안에 있는 원본도 건너뛴다. 확인은 시작 시 만든 realpath 집합 + roomsd와 같은 주기의 증분 갱신.
L5지운 건 다시 안 넣기: 한 번 링크한 realpath는 ~/rooms/.rooms/collect/linked.jsonl에 추가만 한다. 여기 있으면 링크가 사라졌어도 다시 만들지 않는다.
L6목적지: 원본의 repo 이름(find_html repo_key, worktree면 본 repo 이름)과 slug가 같은 owned 방이 있으면 그 방, 없으면 inbox. 방을 새로 만들지 않는다.
L7링크 이름: 원본 파일 이름. 충돌하면 (2), (3)… (스킬과 같은 규칙). 링크는 임시 이름으로 만든 뒤 rename.
L8worktree 복사본: 같은 repo_key + rel_in_repo가 이미 링크돼 있으면 새 경로를 링크하지 않는다.
L9연결 방(linked room) 폴더에는 절대 쓰지 않는다. .rooms/token은 읽지 않는다.

보관소 (archive)

원문은 에이전트가 지우면 끝이므로, 이벤트로 바꾸기 전 단계에서 읽은 바이트를 그대로 복사한다. 형식 변환이 없어서 어댑터가 깨져도 보관은 계속된다.

#규칙
A1위치: ~/Library/Application Support/computer.alto.rooms/archive/<agent>/<YYYY-MM>/<session>.jsonl. ~/rooms에 두지 않는다(대화 원문이 동기화 폴더로 나가지 않게). Time Machine 백업 대상에 그대로 둔다.
A2로그 파일 하나를 읽을 때 같은 바이트 구간 [offset, end)를 보관 사본 끝에 붙인다. 붙이기 전에 사본을 files.archive_len으로 잘라 두므로, 지난번에 커밋 전에 죽어 생긴 꼬리가 지워진다. 사본 fsync 후 DB 트랜잭션(이벤트 + 커서 + archive_len)을 커밋한다. 몇 번을 다시 해도 결과가 같다.
A3원본이 바뀐 파일(C2의 "처음부터 다시 읽기")은 기존 사본을 건드리지 않고 <session>.2.jsonl로 새 사본을 시작한다. 원문은 덮어쓰지 않는다.
A4Codex가 압축한 .jsonl.zst: 압축을 푼 내용이 이미 보관한 사본과 같은 길이, 같은 해시면 건너뛴다. 다르면 A3처럼 새 사본.
A5원본 로그가 24시간 동안 바뀌지 않으면 사본을 zstd(레벨 9)로 압축해 .jsonl.zst로 바꾸고 원래 사본을 지운다. 이후 그 원본에 새 줄이 붙으면 A3처럼 새 사본.
A6첫 실행 때는 디스크에 남아 있는 로그 전부를 보관한다(색인의 30일과 무관). 지금 남은 게 앞으로 남을 전부이기 때문이다. 백그라운드에서 최신 파일부터.
A7보관소는 수집기가 지우지 않는다. 지우는 기능(기간 설정, 세션 단위 삭제)은 다음 단계.
A8검색 발췌와 나중의 대화 보기는 원본 로그 → 보관 사본 → preview 순서로 읽는다. 이벤트의 src_* 위치는 원본 기준이고, 사본은 같은 바이트를 같은 순서로 가지므로 archive_path + (원본 offset − 사본 시작 offset)으로 찾는다.

sources 싱크

모든 file.written(시점 무관)에 대해 v2.1 형식 그대로 sources.json을 병합한다. 같은 경로는 writtenAt이 같거나 새로울 때만 덮고, 임시 파일 + rename. find_html.py와 동시에 쓸 수 있으므로 쓰기 직전에 다시 읽어 병합한다.

8. 검색 (FTS5)

FTS5는 SQLite에 내장된 전문 검색이다. "단어 → 그 단어가 나오는 행" 색인을 미리 만들어 두고 MATCH로 찾는다. 관련도 정렬(bm25)과 발췌를 지원한다.

  • 열: user_text, assistant_text, tool_text, identifiers(경로와 식별자를 / . _ -, camelCase로 쪼갠 형태). 토크나이저는 _ . - / +를 토큰 안에 둬서 파일 경로가 그대로 맞는다.
  • contentless(D8): 색인만 저장하고 원문은 없다. 결과 행 → events의 src_*로 원본 로그를 열어 해당 줄만 읽고 발췌를 만든다. 원본이 사라졌으면 보관 사본(A8), 그것도 없으면 preview로 대신한다.
  • 범위: 색인은 최근 30일(history_days)만. 보관소는 전부를 가지므로, 나중에 범위를 넓히고 싶으면 보관소를 하나의 로그 루트로 다시 색인한다.
  • 가중치: bm25(messages_fts, 1.0, 1.0, 0.4, 0.6). 같은 점수면 최근 순.
  • CLI: rooms-collect search "pricing plan" [--agent codex] [--cwd PATH] [--since 7d] [--json] [--limit 20]. 결과는 세션 단위로 묶어 세션 제목, cwd, 시각, 발췌, 이어가기 명령(claude --resume <id>)을 준다.
  • 검색은 DB를 읽기 전용 연결로 연다(WAL이라 쓰기 중에도 일관된 스냅샷).
SELECT e.agent, e.session, e.ts, e.src_path, e.src_offset, e.src_len, e.preview,
       bm25(messages_fts, 1.0, 1.0, 0.4, 0.6) AS score
FROM messages_fts JOIN events e ON e.rowid = messages_fts.rowid
WHERE messages_fts MATCH ?1
ORDER BY score, e.ts DESC LIMIT ?2;

11. 장애와 예산

상황동작
어댑터 파싱 실패그 파일만 C4 정책. 다른 파일, 다른 에이전트는 계속.
로그 형식 변경해당 어댑터의 실패율이 오르면 ~/rooms/.rooms/collect/status.json에 기록. 앱 업데이트로 어댑터 수정. 수동 대안은 스킬.
DB 손상, 스키마 변경삭제 후 재생성(D5). 링크 중복은 L4, L5가 막는다.
수집기 비정상 종료앱이 지수 백오프로 재시작(최대 5회/10분). 트랜잭션 덕분에 재시작 후 이어서.
roomsd 꺼짐영향 없음. 링크는 다음 roomsd 시작 때 스캔으로 반영.
디스크 가득커밋 실패 → 커서가 안 올라가므로 다음 번에 다시 시도. 링크는 계속 시도.

예산 (목표치, 측정해서 확인)

  • 유휴 상주 메모리 ≤ 20 MB (SQLite 페이지 캐시 상한 4 MB 포함).
  • 평상시 CPU: 새 줄이 없으면 0에 가깝게(FSEvents 대기).
  • 디스크(색인): 원문 미복사. 30일치 로그 총량의 약 15~30% 예상 측정 필요.
  • 디스크(보관소): 압축 후 원본 로그의 약 10~20% 예상(JSON 텍스트는 zstd 압축률이 높다) 측정 필요. 하루 이상 지난 세션만 압축 상태로 있다.
  • 첫 색인: 100 MB 로그 기준 1분 이내, 백그라운드 우선순위.

16. 구현 메모 (2026-10-09)

구현하면서 위 본문과 달라진 점. 본문보다 이 절이 우선한다.

항목달라진 점과 이유
FTS별도 fts 싱크 없이, 이벤트를 넣는 같은 트랜잭션에서 색인 행을 넣는다. 이벤트와 색인이 어긋날 틈이 없고 커서가 하나 준다.
sourceslinker와 한 패스(커서 linker)로 합쳤다. 둘 다 "파일이 실제로 있나, realpath는 뭔가"를 먼저 알아야 해서. find_html.py처럼 존재하는 파일만 기록한다.
L1linkerSince는 state.json에만 둔다. DB는 캐시라서 거기 두면 재생성 때 의미가 없다.
L2재확인은 60초 이내에 기록된 쓰기에만 한다(앱을 다시 켰을 때 오래된 이벤트마다 기다리지 않게). 셸 추정 쓰기는 파일 mtime ≥ 이벤트 시각 − 2초일 때만 인정.
L3rooms-core::rules 무시 규칙은 따로 적용하지 않았다. 원본은 ~/rooms 밖에 있고, 링크 자체는 roomsd가 평소 규칙으로 다룬다.
L4이미 링크된 realpath 집합은 링크 후보가 생긴 패스에서만 ~/rooms를 한 번 훑어 만든다(증분 갱신 대신).
L7symlink(2)는 원자적이고 이미 있으면 실패하므로 임시 이름 + rename을 쓰지 않는다. rename은 오히려 같은 이름을 덮어쓸 수 있다.
L8linked.jsonl에 repo, rel도 적어 worktree 중복을 DB 없이 판단한다.
