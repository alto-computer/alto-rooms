Alto Rooms v2 — 묻기 (Ask)

Spec · 2026-10-06 · author: jun-hash · branch feat/v2-ask · 선행: 2026-10-05-alto-rooms-v1-spec.html (S4 Handoff 예약 seam을 이 문서가 확정)

0. Overview 🟢

Problem

에이전트가 만든 HTML 아티팩트를 Rooms에서 읽다가 궁금한 게 생기면, 그 문서를 만든 터미널 대화를 찾아가서 묻고 다시 돌아와야 한다. 이 왕복이 사용자가 꼽은 가장 큰 시간 손실이다.

Goal (1줄)

문서 탭에서 ⌘J로 둥근 묻기 바를 열고 질문하면, 그 문서를 만든 에이전트 대화의 맥락으로 답이 바 위에 돌아온다 — Rooms는 사용자의 에이전트 CLI를 실행하고 그 stdout을 보여 줄 뿐이다.

설계 원칙 (사용자 결정)

  • 단순하게. Rooms의 관심사는 "AI에 연결"까지. 에이전트별 출력 형식·세션 구조를 코드가 알지 않는다.
  • claude, codex 어디든. 에이전트 지식은 설정 파일의 명령 템플릿(argv 배열)뿐. 새 에이전트 = 설정 한 블록.
  • 대화가 이미 끝났을 수 있으니 매번 새 프로세스로 resume(포크)해서 묻고, 답은 stdout 일반 텍스트로 받는다.
  • UI는 Granola 채팅바처럼. ⌘J로 켜고 끈다. 기본은 켜짐(앱을 켤 때마다 켜진 상태, 저장 안 함. 처음 열 때는 포커스를 가져가지 않는다).

Out of scope (v2)

  • 스트리밍 — 중간 출력 이벤트도, JSON 파싱도 없다. claude/codex/aside 모두 stdout에 최종 답만 끝에 한 번 쓰므로(실측) 답은 ask.done 한 번에 온다.
  • 방 단위 묻기, Journal에서 묻기, 여러 문서를 묶어 묻기.
  • 답을 "문서로 저장" — 답에는 "Copy"만 있다.
  • 다른 기기(Mac mini)로 보내기, 원격 웹 뷰에서 묻기(read_only면 묻기 불가).
  • 살아 있는 터미널 세션을 inbox 파일로 깨우기. 세션 ID 자동 채우기(온보딩 스킬이 sessions를 기록하게 하는 건 별도 작업).
  • 설정 UI. agents.toml은 손으로 고친다.

리뷰 시 확인할 점

"Rooms는 AI를 돌리지 않는다"(v1 원칙)를 어기지 않는가? → 모델·프롬프트 엔지니어링·API 키 없음. 사용자 CLI를 실행하고 텍스트를 중계만 한다. v1 스펙의 "결과는 폴더로만 돌아온다"는 묻기 답은 stdout으로 받는다로 이 문서가 바꾼다.

1. Requirements 🟢

User Stories

  • US-1 문서를 읽다가 ⌘J를 누르고 질문을 쓰면, 그 문서를 만든 에이전트가 원래 대화 맥락을 가진 채 답한다.
  • US-2 답을 보고 이어서 물으면 앞의 문답을 기억한 채 답한다.
  • US-3 세션 정보가 없는 문서도 물을 수 있다(새 대화가 그 파일을 읽고 답한다).
  • US-4 탭을 닫았다 다시 열거나 앱을 재시작해도 그 문서의 대화가 남아 있다.
  • US-5 오래 걸리면 멈출 수 있고, 실패하면 이유를 본다.
  • US-6 claude-code가 아닌 다른 에이전트(codex, aside 등)도 설정만으로 붙인다.

  • 바는 문서 탭에만 있다. 방·Journal·노트·새 탭·플러그인 탭에서는 ⌘J가 아무 일도 안 한다.
  • 대화 시트는 이 문서의 대화에 턴이 하나라도 있으면 바 위에 펼쳐진다. 최대 높이 50vh, 넘치면 시트 안에서 스크롤, 새 답이 오면 맨 아래로.
  • UI 문구는 모두 영어(프로젝트 규칙, 기존 앱의 "Find", "Journal"과 같게; 짧은 sentence case). 입력 칸 "Ask about this doc…", 보내기 aria-label "Send", 칩 기본값 "Default agent". 메뉴 View → "Ask Bar".
  • 시트 머리: {agent} · continuing the thread that made it(resume) 또는 {agent} · new conversation(new). 불러오기 실패: "Couldn't load the conversation" + Try again.
  • 대기 중(Codex처럼): muted 회색 "Thinking" 위로 왼쪽→오른쪽 shimmer(약 1.6초 반복, prefers-reduced-motion이면 정지) + muted "(Ns)"(startedAt부터 1초마다 갱신) + 오른쪽 Stop. 이미지 없음. 입력 칸은 읽기 전용(포커스·Esc는 동작), 보내기 잠김. 끝나면 입력 칸에 다시 포커스.
  • 답은 마크다운 렌더(react-markdown 새 의존성 — 앱에 렌더러가 없음. raw HTML은 기본값대로 렌더하지 않음). 답 아래 "Ns · Copy". 멈춘 턴은 "Stopped". 실패면 빨간 대신 muted 색 에러 문구 + stderr 마지막 줄 + Retry.
  • 빨간색(thread)은 보내기 버튼 하나뿐(Alto DS 규칙).
  • Esc 또는 바깥 클릭: 시트가 펼쳐져 있으면 시트만 접는다(바는 남음). 문서 iframe 안 클릭도 바깥 클릭이다(창 blur + 포커스가 iframe으로 감). 접힌 상태에서 바에 포커스하면 다시 펼친다.
  • 바에 포커스가 있으면(Granola처럼) 테두리가 primary 색 1px로 바뀌고 같은 색의 옅은 바깥 링(4px)이 생긴다. 크기·배치는 그대로.

2. Business Logic & Policy 🟢

Core Rules

  1. R0 meta 검증(문서는 신뢰하지 않는 입력): source.agent, source.session은 ^[A-Za-z0-9][A-Za-z0-9_.:-]{0,127}$일 때만 쓴다(첫 글자가 -면 플래그로 해석될 수 있으므로 금지). 아니면 없는 것으로 본다. source.cwd는 절대경로이면서 존재하는 디렉터리일 때만 쓴다.
  2. R1 에이전트 선택: source.agent가 있고 그 이름의 프로필이 있으면 그것. 아니면 default 프로필(기본값 claude-code).
  3. R2 모드: resume은 세 조건이 다 맞을 때만 — source.session이 있음 · R1에서 고른 프로필 이름 == source.agent(다른 에이전트의 세션을 섞지 않는다) · 프로필에 resume이 있음. 아니면 new.
  4. R3 실행 위치(cwd): source.cwd(R0 통과)면 그것, 아니면 원본 파일 realpath의 부모 디렉터리. resume이 세션을 찾는 데는 cwd가 필요 없다(claude 실측) — cwd는 에이전트가 상대경로로 파일을 읽을 때를 위한 것. resume이 실패하면(세션 삭제 등) 그냥 exit≠0 → failed; Rooms는 stderr를 해석해 new로 자동 전환하지 않는다.
  5. R4 프롬프트(Rooms가 만드는 유일한 텍스트): preamble + 문서 경로 + 이 대화의 이전 done 턴 최대 6개(오래된 것부터, 합계 24,000자 넘으면 오래된 턴부터 버림) + 질문. 형식은 §6.3에 고정.
  6. R5 이어 묻기: 새 세션 ID를 파싱하지 않는다. 매 턴 원래 source.session에서 다시 resume(포크)하고, 맥락은 R4의 이전 문답으로 잇는다.
  7. R6 셸 없음: 템플릿은 argv 배열. {prompt} {session} {file} {cwd}는 각 원소 안에서 문자열 치환만. 첫 원소는 실행 파일. sh -c 금지.
  8. R7 동시성: fileKey당 running 턴 최대 1개. 전역 동시 실행 상한 4개(넘으면 409 ask_capacity).
  9. R8 상한: 실행 10분 넘으면 종료(failed, "시간 초과"). stdout 1 MiB 넘으면 종료(failed, "답이 너무 길어요"). stderr는 마지막 4 KiB만 보관.
  10. R9 저장 위치: <home>/.rooms/asks/<fileKey>.jsonl. 원본·연결 폴더에는 아무것도 쓰지 않는다.
  11. R10 바 표시: 켜짐/꺼짐은 앱 메모리의 전역 boolean, 시작값 true, 저장하지 않는다. 입력 칸 포커스는 사용자가 켤 때(false→true)만. 진행 중인 묻기와 독립.
  12. R11 읽기 전용: info.readOnly면 POST/DELETE는 기존 write guard가 403으로 막는다(Asks는 read-only를 모른다). 앱은 바를 렌더하지 않는다(⌘J 무시).
  13. R12 환경: 자식 프로세스는 roomsd의 환경 + 로그인 셸에서 얻은 PATH. roomsd는 시작할 때 이 조회를 백그라운드로 1회 띄우고 기다리지 않는다(Asks::resolve_login_path): $SHELL -l -c 'printf "__ROOMS_PATH__%s" "$PATH"'($SHELL이 없으면 /bin/zsh), stdin /dev/null, 2초 타임아웃. 출력에서 마지막 sentinel __ROOMS_PATH__ 뒤의 첫 줄만 trim해서 PATH로 쓴다. 그래서 .zprofile이 앞에 찍는 글자도, .zlogout이 뒤에 찍는 글자도 무시된다. sentinel이 없거나, 값이 비었거나, 셸이 0이 아닌 코드로 끝나거나, 타임아웃이면 결과를 버린다. 결과가 도착하기 전에(또는 버려지면) 시작된 ask는 roomsd 자신의 PATH를 그대로 쓴다. stdin은 /dev/null. 새 프로세스 그룹으로 띄운다.

Cross-field & Temporal Invariants

  • I1 한 fileKey의 jsonl은 턴 시작 시 running 레코드 1줄, 끝날 때 최종 레코드 1줄을 append. 읽을 때 같은 id는 마지막 줄이 이긴다. → 크래시로 끝 레코드가 없으면 그 턴은 running으로 남는데, roomsd 시작 시 메모리에 실행 중이 아닌 running 턴은 읽을 때 failed("Rooms가 다시 시작돼서 중단됐어요")로 보고한다.
  • I2 이벤트 순서: 한 턴에 대해 ask.started 1회 → ask.done 정확히 1회. 중간 이벤트는 없다.
  • I3 ask.done을 보내기 전에 최종 레코드가 디스크에 append돼 있다(이벤트를 받은 클라이언트가 GET하면 최종 상태를 본다).
  • I4 턴의 agent/mode는 시작 시 정해지고 바뀌지 않는다(나중에 문서 meta가 바뀌어도 기록은 그대로).

Recovery / Retry Policy

  • 자동 재시도 없음. 실패한 턴 아래에 "Retry" 링크 — 같은 질문으로 새 턴 POST.
  • agents.toml은 매 POST마다 다시 읽는다(캐시 없음, 파일 작음). 고치고 바로 다시 물으면 된다.
  • SSE 끊김: v1 규칙(재연결 시 resync)대로, 앱은 재연결 후 열린 문서의 GET /v1/asks를 다시 부른다.

#결정근거 / 버린 대안
D1실행은 roomsd(rooms-core의 Asks)프로토콜만 쓰는 다른 클라이언트도 같은 기능. Tauri에서 실행하면 데스크톱 전용이 된다.
D2에이전트 지식 = agents.toml의 argv 템플릿뿐코드에 "claude" 문자열 없음(기본 프로필 상수 제외). 플러그인 슬롯으로 하자니 플러그인은 명령 실행 불가(v1 플러그인 스펙).
D3stdout = 일반 텍스트, 파싱 안 함stream-json 파싱은 에이전트마다 달라 결합. 대가: claude 텍스트 모드는 끝에 한 번에 나온다.
D4이어 묻기 = 원 세션 resume(포크) + 이전 문답 프롬프트 첨부새 session_id 파싱 불필요. 원 세션이 터미널에 열려 있어도 안전.
D5셸 없음, argv 배열 템플릿셸 인용 파싱 불필요 + 주입 차단.
D6기록은 .rooms/asks/<fileKey>.jsonl, append-only방 이동·심링크에도 같은 대화. SQLite 대신 파일 — v1 "파일이 진실" 원칙.
D7⌘J 토글은 네이티브 메뉴 accelerator + 페이지 키 핸들러 둘 다포커스가 문서 iframe 안이면 페이지 keydown이 안 온다(⌘B와 같은 구조).

Cluster Facades

  • 서버 덩어리 = Asks 하나. routes는 Asks만 부른다. 템플릿·프롬프트·로그·프로세스는 asks 모듈 밖으로 안 나간다(pub(crate)).

  • TS: startAsk, askThread, cancelAsk, AskBar, useAskBarOpen, 액션 "toggle-ask", 메뉴 id MENU_TOGGLE_ASK (menu://toggle-ask).

5. Seams 🟢

§4 다이어그램 화살표 하나당 블록 하나. call-site 먼저 → frozen signature → 3줄 계약.

S1: AskBar → roomsd (HTTP + SSE)

앱과 코어 사이 유일한 묻기 경로. 프로토콜 v1에 엔드포인트·이벤트를 더한다(PROTOCOL_VERSION은 "1" 유지 — 추가만).

call-site
// apps/desktop/src/ask/askStore.ts
const turn = await client.startAsk({ roomId: artifact.roomId, artifactId: artifact.id, question });
// → turn.status === "running"; 끝나면 SSE ask.done 이 turn.id 로 들어온다.
// SSE ask.started 가 202보다 먼저 올 수 있다 → askStore 는 id 기준 upsert (먼저 온 쪽이 턴을 만든다)
const thread = await client.askThread(artifact.fileKey);     // 탭 열 때·재연결 때
await client.cancelAsk(turn.id);                              // 멈추기
frozen signature
POST   /v1/asks                 body StartAsk            → 202 AskTurn        (write guard + bearer)
GET    /v1/asks?fileKey={key}                            → 200 AskTurn[]      (오래된 것 → 최신)
DELETE /v1/asks/{askId}                                  → 204                (write guard + bearer, 멱등)

type StartAsk = { roomId: RoomId; artifactId: ArtifactId; question: string };
type AskStatus = "running" | "done" | "failed" | "cancelled";
type AskMode = "resume" | "new";
type AskTurn = {
  id: string; fileKey: string; question: string; answer: string;
  agent: string; mode: AskMode; status: AskStatus;
  error: string | null; startedAt: string; endedAt: string | null;   // RFC3339
};
// EventKind 추가
{ type: "ask.started", turn: AskTurn }
{ type: "ask.done",    turn: AskTurn }                                  // 최종 상태, answer 전체 포함

// client.ts
startAsk(req: StartAsk): Promise<AskTurn>
askThread(fileKey: string): Promise<AskTurn[]>
cancelAsk(askId: string): Promise<void>
건너감↓ (roomId, artifactId, question) / askId · ↑ AskTurn
제어·상태 소유roomsd가 턴과 기록을 소유. 앱은 SSE를 받아 화면 상태만 가진다(진실은 askThread).
상대편 보장202를 받았으면 그 턴에 대해 ask.done이 반드시 1회 온다(I2). ask.done.turn.answer가 답 전체다.

S2: roomsd routes → Asks (facade)

HTTP를 벗겨 낸 도메인 호출.

call-site
// crates/roomsd/src/routes.rs
let turn = state.asks.start(&req.room_id, &req.artifact_id, &req.question)?;   // AskError → ApiError
let turns = state.asks.thread(&q.file_key)?;
state.asks.cancel(&ask_id);
frozen signature
pub struct Asks { /* RoomsCore 핸들, 실행 중 맵, 경로 */ }
impl Asks {
    pub fn new(core: RoomsCore, login_path: Option<String>) -> Self;
    /// 검증·템플릿 해석·running 기록·프로세스 시작까지 동기로 끝내고 반환. 출력은 백그라운드 태스크가 emit.
    pub fn start(&self, room: &RoomId, artifact: &ArtifactId, question: &str) -> Result<AskTurn, AskError>;
    pub fn thread(&self, file_key: &str) -> Result<Vec<AskTurn>, AskError>;
    pub fn cancel(&self, ask_id: &str);          // 없거나 끝났으면 no-op
    pub async fn shutdown(&self);                // SIGTERM 시 실행 중 전부 kill, ≤700ms 기다려 cancelled 기록(앱은 1초 줌)
}
pub enum AskError { BadRequest(String), NotFound, Busy, Capacity, AgentConfig(String), Io(String) }   // read-only는 write guard가 403
건너감↓ 식별자 + 질문 문자열 · ↑ AskTurn / AskError
제어·상태 소유Asks가 실행 중 맵(askId → (fileKey, kill handle))과 기록을 소유. routes는 무상태.
상대편 보장start가 Ok면 running 레코드가 디스크에 있고 ask.started가 이미 emit됐다. spawn 실패도 Ok(턴은 곧 failed로 done).

S5: Asks → AskLog

let log = AskLog::new(home.join(".rooms/asks"));
log.append(&turn)?;                       // running 시작, 최종 각각 1줄
let turns = log.read(&file_key)?;         // id별 마지막 줄 승리, startedAt 오름차순

pub(crate) struct AskLog { dir: PathBuf }
impl AskLog {
    pub fn append(&self, turn: &AskTurn) -> std::io::Result<()>;   // O_APPEND, 한 줄 = 한 write, 디렉터리 없으면 생성(0700)
    pub fn read(&self, file_key: &str) -> std::io::Result<Vec<AskTurn>>;  // 파일 없음 = 빈 Vec, 깨진 줄은 건너뜀
}
건너감↓ AskTurn · ↑ AskTurn[]
제어·상태 소유파일이 진실. 쓰는 쪽은 Asks 하나(roomsd는 home당 1개 — v1 flock).
상대편 보장append가 Ok를 반환하면 그 줄은 다음 read에 보인다. fileKey는 파일명 안전 문자열이라는 v1 보장에 기댄다(구현 시 [A-Za-z0-9_-] 아닌 키는 BadRequest).

S6: Asks → spawn_agent → 에이전트 CLI

Rooms 밖으로 나가는 유일한 출구(v1의 "handoff out").

let Running { killer, done } = spawn_agent(SpawnSpec { argv, cwd, path_env, limits })?;   // Err = spawn 실패
killer.kill(Reason::Cancelled);                             // 멈추기: killpg(SIGTERM) → 3초 후 SIGKILL (Shutdown은 300ms)
let outcome: Outcome = done.await?;                         // Exited{code, stdout, stderr_tail} | Killed{reason, stdout}

pub(crate) struct SpawnSpec { pub argv: Vec<String>, pub cwd: PathBuf, pub path_env: Option<String>, pub limits: Limits }
pub struct Limits { pub timeout: Duration /*600s*/, pub max_stdout: usize /*1 MiB*/, pub stderr_tail: usize /*4 KiB*/, pub kill_grace: Duration /*3s*/ }
pub(crate) enum Reason { Cancelled, Timeout, TooLong, Shutdown }
pub(crate) enum Outcome { Exited { code: i32, stdout: String, stderr_tail: String }, Killed { reason: Reason, stdout: String } }
건너감↓ argv, cwd, PATH · ↑ 종료 결과 + stdout 전체
제어·상태 소유자식 프로세스 그룹은 핸들이 소유. 핸들이 drop되면 kill(고아 없음).
상대편 보장에이전트 CLI는 답을 stdout에 쓰고 끝나면 종료한다 — 그 외 가정 없음. stdout은 끝까지 모아 lossy UTF-8로 바꾸고 ANSI 이스케이프(\x1b\[[0-9;?]*[ -/]*[@-~])를 지운 뒤 앞뒤 공백 trim.

제어·상태 소유seq와 브로드캐스트는 RoomsCore 소유. Asks는 emit만 요청.
상대편 보장emit된 이벤트는 기존 SSE 스냅샷→버퍼 규칙을 그대로 따른다(ask 이벤트도 seq를 받는다).

6. Contracts 🟢

6.1 Asks::start

항목내용
Inputsroom: 존재하는 방 id · artifact: 그 방의 문서 id · question: trim 후 1–8,000자
Preroomsd가 read-only 아님 · 같은 fileKey running 없음 · 전역 running < 4
순서① 검증 → ② artifact·file_abs 조회 → ③ AgentProfiles load+plan → ④ prior = thread(fileKey)의 done 턴 → ⑤ build_prompt → ⑥ render → ⑦ running 레코드 append → ⑧ 실행 중 맵 등록 + ask.started emit → ⑨ spawn(실패 시 즉시 failed 마감) → 반환
OutputsAskTurn{status: running, answer: "", endedAt: null}
Post정확히 한 번 ask.done(I2). 최종 레코드 append 후 emit(I3). 실행 중 맵에서 제거.
Errors§3 표: BadRequest/NotFound/ReadOnly/Busy/Capacity/AgentConfig/Io. ①–⑥ 실패는 디스크·이벤트 흔적 없음.

6.2 agents.toml 형식 + 기본값

# ~/rooms/.rooms/agents.toml — 없으면 아래 기본값과 같다. Rooms는 이 파일을 쓰지 않는다.
default = "claude-code"
# preamble = "..."            # 생략 시 §6.3 기본 문구

[agents.claude-code]
resume = ["claude", "-p", "--resume", "{session}", "--fork-session", "--no-session-persistence", "--setting-sources=user", "--tools=Read,Grep,Glob", "{prompt}"]
new    = ["claude", "-p", "--no-session-persistence", "--setting-sources=user", "--tools=Read,Grep,Glob", "{prompt}"]

[agents.codex]
resume = ["codex", "exec", "fork", "{session}", "-c", "sandbox_mode=\"read-only\"", "--ephemeral", "--skip-git-repo-check", "{prompt}"]
new    = ["codex", "exec", "-s", "read-only", "--ephemeral", "--skip-git-repo-check", "{prompt}"]

[agents.aside]
resume = ["aside", "session", "resume", "{session}", "{prompt}"]
new    = ["aside", "exec", "{prompt}"]
  • 플레이스홀더: {prompt} {session} {file} {cwd}. 그 외 {…}는 그대로 둔다(에러 아님).
  • 검증: new 필수, 비어 있지 않음, 첫 원소에 { 없음. 실패 → AgentConfig("agents.codex.new: …").
  • 읽기 전용(기본 템플릿 한정의 계약): claude는 --tools=로 쓸 수 있는 도구 자체를 Read/Grep/Glob로 제한(--allowedTools는 사전 승인일 뿐이라 쓰지 않는다), codex는 read-only 샌드박스. aside는 브라우저 에이전트라 파일 수정 도구 개념이 다르다 — preamble의 "고치지 마세요"에 맡긴다. 사용자가 고친 템플릿은 Rooms가 보장하지 않는다.
  • 남의 폴더 설정을 읽지 않기: -p는 작업 폴더 신뢰 확인을 건너뛰는데, cwd는 믿을 수 없는 문서 메타(rooms:cwd)나 문서 폴더에서 온다. 그래서 claude는 --setting-sources=user로 사용자 설정만 읽는다 → 그 폴더의 .claude/settings.json·settings.local.json(project/local 설정과 그 안의 hooks)은 로드·실행되지 않는다. 실측(2026-10-06, claude 2.1.291, 빈 임시 폴더): claude -p --no-session-persistence --setting-sources=user --tools=Read,Grep,Glob "Reply with exactly: pong" </dev/null → pong, exit 0.
  • 흔적 안 남기기: claude --no-session-persistence, codex --ephemeral → 묻기마다 포크 세션 파일이 생기지 않아 /resume 목록이 지저분해지지 않는다. 원 세션도 그대로(claude --fork-session, codex exec fork).
  • aside는 포크가 없다: aside session resume은 실제 세션에 이어 붙는다 → 질문과 답이 Aside 앱의 그 세션에도 남는다(오히려 "만든 대화로 바로 간다"에 가장 가깝다). aside 세션은 계정 단위라 다른 기기에서 만든 세션도 이어진다.
  • --tools=·--setting-sources=처럼 값을 =로 붙여 쓴다: claude의 --tools/--allowedTools는 가변 인자라 띄어 쓰면 뒤의 {prompt}까지 삼킨다(실측: "Input must be provided" 에러). codex exec fork에는 -s가 없어서 -c sandbox_mode=…를 쓴다.
  • 실측(2026-10-06, 로컬): claude/codex/aside 셋 다 stdout = 최종 답만, 진행 로그는 stderr. claude resume은 다른 cwd에서도 세션을 찾았다. aside stdout 끝에 ANSI 리셋 코드가 붙는다 → Rooms는 stdout에서 ANSI 이스케이프(ESC[…)를 일반적으로 제거한다(에이전트별 처리 아님).

6.4 Asks::thread / cancel

  • thread(fileKey): AskLog.read 결과에서, running인데 실행 중 맵에 없는 턴은 failed + "Stopped because Rooms restarted"로 바꿔 반환(I1). 실행 중 턴은 running 그대로(answer 빈 문자열) → 탭을 다시 열어도 대기 표시가 보인다(AC-14).
  • cancel(id): 맵에 있으면 kill(Reason::Cancelled). 종료 처리는 일반 경로(최종 레코드 + done)가 한다.

③ 입력 & 출처

④ 주요 결정

  • 결정론(코드): 에이전트·모드·cwd 선택(R1–R3), 프롬프트 조립(R4), 상한(R8).

⑤ 에러 & 폴백

§3 표. 동기 단계 실패는 HTTP 에러로 바에 한 줄(입력 내용 유지). 비동기 실패는 턴에 failed 표시 + "Retry".

⑥ 동작 결과

⑦ 연결

S1, S2, S3, S4, S5, S6, S7.

F2: 멈추기 · 시간 초과 · 종료

① 트리거

"Stop" 클릭(DELETE), 10분 타이머, stdout 1 MiB, roomsd 종료(Asks::shutdown; 앱 종료 시 사이드카도 종료).

② 워크플로우

kill 요청 → killpg(SIGTERM) → 3초 안에 안 끝나면 SIGKILL → wait가 Killed(reason) → 최종 레코드(cancelled 또는 failed, 그때까지의 answer 보존) → ask.done.

③ 입력

askId(DELETE) 또는 내부 타이머.

④ 주요 결정

프로세스 그룹 단위 kill — claude/codex가 띄운 자식(도구 실행)까지 정리. Cancelled/Shutdown → cancelled, Timeout/TooLong → failed.

⑤ 에러 & 폴백

이미 끝난 턴에 DELETE → 204 no-op. shutdown 중 기록 실패 → 다음 시작 때 I1 규칙으로 failed 표시.

⑥ 동작 결과

바 잠금 해제, 부분 답 + "멈췄어요" muted 표시.

⑦ 연결

S1(DELETE), S6(kill).

F3: 대화 다시 보기

① 트리거

AskBar가 마운트될 때(바가 열린 상태로 문서 탭이 보이거나, ⌘J로 열 때) 그 fileKey 캐시가 없으면. SSE 재연결(resync) 때는 캐시된 fileKey 전부 다시.

② 워크플로우

askThread(fileKey) → 캐시 교체 → 이후 SSE ask.*로 갱신(fileKey가 맞는 것만).

③ 입력

artifact.fileKey.

④ 주요 결정

캐시 병합 규칙: id 기준 upsert. 상태 우선순위 terminal(done/failed/cancelled) > running — 늦게 도착한 running(202 응답 등)이 이미 끝난 턴을 되돌리지 않는다.

⑤ 에러 & 폴백

GET 실패 → 시트에 "대화를 불러오지 못했어요" + 다시 시도. 바 입력은 그래도 가능.

⑥ 동작 결과

턴이 있으면 시트가 펼쳐진 상태로 시작, 없으면 바만.

⑦ 연결

S1(GET + SSE).

F4: 바 켜고 끄기 (⌘J)

① 트리거

⌘J(macOS) / Ctrl+J(그 외) — 페이지 keydown(keyAction에 j: "toggle-ask") 또는 네이티브 메뉴 accelerator(menu://toggle-ask, 포커스가 iframe 안일 때). 메뉴: View → "묻기 바" CmdOrCtrl+J.

② 워크플로우

AppShell case "toggle-ask" → 활성 탭이 doc이고 readOnly가 아니면 toggle() → 켜질 때 입력 칸 focus.

③ 입력

활성 탭 종류, info.readOnly.

④ 주요 결정

상태는 전역 1개, 시작값 true(기본 켜짐), 저장 안 함(사용자 결정). 켤 때만 입력 칸 focus — 시작 시나 탭을 열 때는 포커스를 가져가지 않는다. 입력 칸 안에서도 동작(토글로 닫아야 하므로). 한글 IME에서도 e.code === "KeyJ"로 잡힘(기존 shortcutLetter).

⑤ 에러 & 폴백

doc 탭이 아니면 무시(아무 표시 없음).

⑥ 동작 결과

바·시트 등장/사라짐. 진행 중 묻기는 영향 없음.

⑦ 연결

10. Senior Review 🟢

10.1 진입점-우선 워크스루

  1. 진입점: 서버는 Asks::start(room, artifact, question) 하나, 앱은 <AskBar artifact/> 하나. "문서 하나와 질문 하나를 주면 턴 하나가 생기고, 끝나면 이벤트가 한 번 온다."
  2. 분리: Asks 안쪽은 넷으로 갈린다 — 무엇을 실행할지(AgentProfiles, 사용자 파일), 무슨 말을 보낼지(build_prompt, 순수), 어떻게 실행할지(spawn_agent, 프로세스), 무엇을 남길지(AskLog, 파일). 에이전트 지식은 첫째에만, Rooms의 문구는 둘째에만 있다.
  3. 흐름: POST → 동기 검증·기록·spawn → 202 → 종료 시 stdout을 기록하고 done 한 번. 앱은 GET + SSE로 화면만 맞춘다.
  4. 계약: 202면 done이 정확히 한 번(I2), done 전에 디스크(I3), 셸 없음(R6), 원 세션 불변(포크 템플릿).

3축 성공 기준

  • interface — 시그니처만 보고 호출 가능 (start/thread/cancel, AskBar artifact)
  • data flow — 소유가 한쪽: 턴·기록은 roomsd, 템플릿은 사용자 파일, 화면 상태는 앱
  • behavior — 상태기계 4상태 + I1–I4로 내부를 안 열고 예측 가능

10.2 Senior Q&A

Q1. Resume from fallback cwd silently fails

A. 실측(2026-10-06): claude -p --resume S --fork-session은 세션과 다른 cwd에서도 세션을 찾았다. 그래서 cwd는 세션 찾기와 무관하고, 에이전트가 상대경로를 읽을 때만 쓰인다(R3에 명시). resume이 정말 실패하면(세션 삭제 등) exit≠0 → failed로 끝나고, Rooms는 stderr를 해석해 new로 바꾸지 않는다. 사용자는 실패 문구를 보고 다시 묻는다.

Q2. Default codex resume template is invalid

A. 맞다. codex exec fork에는 -s가 없다. 그래서 -c sandbox_mode="read-only"로 바꿨다(fork도 -c는 받는다). 기본 템플릿 셋(claude/codex/aside)은 manual-test에 "실제 CLI로 resume·new 각 1회" 항목을 두고, 단위 테스트는 기본값이 파싱·검증을 통과하는지만 본다. CLI 플래그는 Rooms가 통제할 수 없으므로 자동 테스트에서 실제 CLI를 부르지 않는다.

Q3. "Read-only" is enforced by which flag?

A. --allowedTools는 사전 승인일 뿐이라는 지적이 맞다. claude는 --tools=Read,Grep,Glob(쓸 수 있는 도구 자체를 제한)로 바꿨고 실측으로 동작을 확인했다. 띄어 쓰면 가변 인자가 프롬프트를 삼켜서 = 형식으로 고정했다. codex는 read-only 샌드박스를 쓴다. 이건 기본 템플릿에 한한 계약이다(§6.2). 사용자가 고친 템플릿과 aside(브라우저 에이전트)는 preamble에 맡긴다.

Q4. Untrusted HTML meta flows into argv

A. R0을 추가했다. agent와 session은 ^[A-Za-z0-9][A-Za-z0-9_.:-]{0,127}$일 때만 쓰고(첫 글자 - 금지라 플래그 주입이 막힌다), 아니면 없는 것으로 보고 new 모드로 간다. cwd는 존재하는 절대 디렉터리일 때만 쓴다. 이 검증은 Asks::start가 S3 plan을 부르기 전에 한다.

Q5. Unknown agent falls back with a foreign session

A. R2를 고쳤다. resume은 고른 프로필 이름이 source.agent와 같을 때만 한다. codex 문서에 codex 프로필이 없으면 default(claude-code)로 new 모드가 되고, 다른 에이전트의 세션 ID는 쓰지 않는다. 422로 막지 않는 이유: 그래도 "이 파일을 읽고 답해"는 쓸모가 있다.

Q6. SSE events can beat the 202

A. askStore는 id 기준 upsert를 한다. 202와 ask.started 중 먼저 온 쪽이 턴을 만든다. 상태 우선순위는 terminal > running이라, 늦게 온 202(running)가 이미 done인 턴을 되돌리지 않는다. S1 call-site와 F1⑥, F3④에 반영했다.

Q7. Is streaming ask.output worth its machinery?

A. 아니다. 실측으로 claude, codex, aside 셋 다 stdout에 최종 답만 끝에 한 번 쓴다. ask.output, UTF-8 이월, thread의 부분 답을 모두 지웠다. 이벤트는 ask.started/ask.done 둘만 남았고, 답은 done에 통째로 실린다. 스트리밍이 필요해지면 그때 추가 이벤트로 넣는다(프로토콜에 추가만 하면 되는 변경).

Q8. Every ask leaves a forked session behind

A. claude는 --no-session-persistence, codex는 --ephemeral을 기본 템플릿에 넣었다. 실측으로 claude 포크가 세션 파일을 남기지 않는 것을 확인했다. aside는 포크가 없어서 실제 세션에 이어 붙고, 이건 의도된 동작으로 문서화했다(Aside 앱의 그 세션에서 문답이 보인다). 이전 문답은 Rooms가 프롬프트에 붙이므로 매 턴 버려지는 포크로도 대화가 이어진다.

  • 못 찾으면 알린다. new 모드 시트 머리: "{agent} · new conversation — couldn't find the thread that made this doc".

sources.json 형식

{ "version": 1,
  "sources": {
    "/abs/realpath/of/doc.html": { "agent": "claude-code", "session": "0a295c02-…", "cwd": "/abs/cwd", "writtenAt": "2026-10-01T00:22:51Z" }

  • 쓰기: 기존 파일을 읽어 병합 → 같은 경로는 writtenAt이 같거나 더 새로울 때만 덮어씀 → 임시 파일 + rename(원자적). 파일이 깨져 있으면 빈 것으로 보고 새로 씀.
