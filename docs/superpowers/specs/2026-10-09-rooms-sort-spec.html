rooms-sort — inbox를 비우는 분류기

Spec · 2026-10-09 (rev 4, 구현)author: jun-hash선행: rooms-collect-spec, v1-spec (artifacts/move)모델: TypeSafe Jev

rooms-collect는 새 문서를 모으기만 하고, 어느 룸에 둘지는 전부 rooms-sort가 정한다. 규칙은 다섯 개이고 위에서부터 처음 맞는 하나가 결과가 된다. 앞의 두 규칙은 키 없이 돌고, Jev가 필요한 규칙은 사용자가 TypeSafe API 키를 넣었을 때만 켜진다.

0. 개요

바뀐 결정 1 (사용자): rooms-collect 스펙 §0은 "Rooms는 AI를 부르지 않는다"였다. 수집이 자동이 되면서 inbox가 쌓이므로 분류도 Rooms의 역할로 본다. AI 호출은 사용자가 키를 넣었을 때만 일어나고, 코어(roomsd)와 collect는 여전히 AI를 모른다.

바뀐 결정 2 (사용자): 분류 기준을 한곳에 모은다. collect가 하던 "repo 이름과 같은 룸에 바로 넣기"(collect L8)를 rooms-sort의 첫 규칙으로 옮기고, collect는 언제나 inbox에 링크한다.

결합: rooms-sort는 roomsd의 이미 있는 공개 API(rooms-mcp와 같은 것)와 ~/rooms 아래 파일 두 개(.rooms/collect/linked.jsonl, .rooms/token)만 읽는다. 새 API는 없다.

Goal

  • 분류 기준이 이 문서의 표 하나(§2)와 코드의 함수 하나(rules::decide)에 그대로 대응한다. 결정마다 어느 규칙이 왜 적용됐는지 기록되고 rooms-sort log로 보인다.
  • 키가 없어도 지금과 같은 결과(이름 일치 룸으로 이동)를 낸다.
  • 키가 있으면 확신 높은 문서는 기존 룸으로, 같은 git repo 문서가 3개 쌓이면 그 repo 이름의 새 룸으로 간다. 애매하면 inbox에 남는다.
  • 사람(사용자, rooms 스킬)이 둔 문서는 건드리지 않는다. 모든 이동은 되돌릴 수 있다.
  • 상주 메모리 0. 앱이 1분마다 실행하고, 할 일이 없으면 API 한 번 묻고 끝난다.

Out of scope

  • 주제로 새 룸 이름 짓기(예: "디자인 리서치"). rooms 스킬의 일(§1).
  • inbox 밖 문서 재분류, 룸 간 이동, 룸 병합.
  • TypeSafe 외 제공자. Jev 호출은 jev.rs 한 파일에 가둔다.
  • 앱 안 분류 기록 화면. inbox 위 카드의 상태 한 줄과 "마지막 분류 되돌리기"까지.

1. 역할 분리

문서를 룸에 두는 주체는 셋이다. 누가 시작하는지, 어떤 문서를 다루는지로 나뉜다.

주체누가 시작다루는 문서하는 일하지 않는 일
rooms 스킬사용자가 에이전트에게 요청설치 전 문서, 사용자가 지목한 문서, inbox 전체주제 룸을 제안하고 승인받아 만들고 배치(온보딩 첫 정리, "inbox 정리해줘", "이거 룸에 넣어줘")스스로 실행
rooms-collect앱(상주)설치 후 에이전트가 새로 쓴 HTMLinbox에 링크, 출처를 sources.json에, 링크를 linked.jsonl에 기록룸 고르기
rooms-sort앱(1분마다)collect가 inbox에 링크했고 아직 inbox에 있는 문서만§2 규칙으로 기존 룸 또는 repo 룸으로 이동사람이 둔 문서 건드리기, inbox 밖 이동, 주제 룸 이름 짓기

겹칠 때

  • 스킬이 먼저 옮긴 문서: 이미 inbox에 없으므로 rooms-sort 대상이 아니다.
  • 사용자나 스킬이 inbox에 넣은 문서("이거 inbox에 넣어줘"): linked.jsonl에 없으므로 rooms-sort가 옮기지 않는다.
  • rooms-sort가 옮긴 문서를 사용자가 inbox로 되돌림: 이미 결정한 문서라 다시 옮기지 않는다. 스킬로는 언제든 다시 정리할 수 있다.
  • 스킬이 새 주제 룸을 만듦: 다음 실행부터 Jev의 보기에 들어간다. 룸 목록이 바뀌었으므로 inbox에 남겨 뒀던 문서를 한 번 더 묻는다.

요약하면, 스킬은 사람이 판단을 맡기는 정리이고 rooms-sort는 사람이 아무것도 안 할 때의 기본값이다.

세부 기준

기준내용
N1 git repo원본 경로에서 위로 올라가며 .git을 찾는다. worktree(.git이 파일)는 본 repo 이름, Orca 작업 공간은 프로젝트 이름. 못 찾으면 repo 없음. 폴더 이름은 repo로 쓰지 않는다(collect의 repo_info와 달리 부모 폴더로 대신하지 않음).
N2 일반 이름repo 이름이 Downloads, Desktop, Documents, tmp, temp, docs, notes, scratch, test, tests, out, dist, build, untitled이면 R4 후보가 아니다(R1은 적용). sort.toml의 ignore_names로 늘린다.
N3 표표는 문서당 한 번. 표를 준 문서가 그 사이 inbox를 떠났으면 그 표는 센 수에서 빠진다.
N4 만든 룸이 지워짐R4가 만든 룸을 사용자가 지우면 기억을 지우고 그 repo로는 다시 룸을 만들지 않는다(사용자가 원하지 않은 것으로 본다). 이후 그 repo 문서는 R3까지만 본다.
N5 키 없음R5 no_key는 기록하지 않는다. 키를 넣으면 그 문서들이 바로 R3부터 다시 평가된다.

코드: rules::decide(doc, rooms, memory, jev_answer, config) -> Decision { rule, action, why }는 I/O 없는 순수 함수다. 테스트 이름도 규칙 id를 따른다(r1_name_match_moves, r4_third_vote_creates_room …). Jev 호출은 R1, R2가 맞지 않은 문서에만 한다.

3. Jev 입력과 출력

문서 하나에 호출 하나. 아래가 보내는 것 전부다.

입력 (state + 질문 1개)
제목 ≤ 120자

Artifact 제목. "Canvas 렌더 성능 메모"

위치 ≤ 200자

repo 이름 + repo 안 경로. "rooms-plugin-excalidraw/notes/canvas-perf.html". repo가 없으면 파일 이름만. 홈 경로와 사용자 이름은 보내지 않는다.

본문 발췌 ≤ 2,000자

보이는 텍스트 앞부분. script, style, 태그, 연속 공백 제거.

보기 (criteria) 룸당 ≤ 350자, 합계 ≤ 6,000자

룸 id → "룸 이름 — 포함: 최근 문서 제목 5개(각 60자)". 마지막에 none: "어느 룸에도 뚜렷이 맞지 않음". 합계가 넘치면 최근 활동이 오래된 룸부터 뺀다.

합계 ≈ 1~4k 토큰

룸 10개 기준 약 1.5k 토큰. 문서 1,000개 분류에 약 $0.1 (입력 $0.042/1M, 출력 무료).

→Jevjev-1.13.0
70~500ms→
출력
choice

보기 키 하나. 룸 id 또는 none. 보기 밖 값은 나올 수 없다.

confidence 0~1

R3 기준과 비교하는 값.

probabilities

보기별 확률. 상위 3개만 기록(기준값 조정용).

usage

입력 토큰 수. runs에 합계를 남긴다.

보내지 않는 것: 원본 HTML 전체, 스크립트와 이미지, 에이전트 대화 로그, 세션 id, 홈 경로와 사용자 이름, 다른 inbox 문서, R1·R2로 끝난 문서(이 문서들은 호출 자체가 없음).

  • 모델은 버전을 고정한다(jev-latest는 쓰지 않음).
  • 429, 529는 지수 백오프로 최대 3번. 401은 실행을 멈추고 상태에 "키 오류"를 적는다.

4. 사용자 경험

앱에는 아직 설정 화면이 없으므로, 문제가 보이는 자리인 inbox 룸 위의 카드에서 켜고 끈다.

키 없음

카드: "자동 분류 켜기 — TypeSafe 키를 넣으면 inbox 문서를 맞는 룸으로 옮겨요." 키 입력칸, "키 받기"(console.typesafe.ai/keys), "켜기". 저장하면 테스트 호출 후 "연결됨". 401이면 "키가 맞지 않아요. 콘솔에서 다시 복사해 주세요." 아래에 한 줄: "문서 제목, repo 안 경로, 본문 앞 2,000자가 TypeSafe로 보내져요." 카드는 닫을 수 있고, 닫으면 inbox 머리의 작은 "자동 분류" 버튼으로 남는다. 키가 없어도 R1, R2는 늘 돈다.

키 있음

카드 대신 inbox 머리에 상태 한 줄: "자동 분류 켜짐 · 오늘 12개 이동, 3개 남김 · 2분 전". 누르면 "마지막 분류 되돌리기", "키 지우기", 환경변수 사용 중이면 그 표시.

되돌리기

rooms-sort undo 또는 버튼. 그 실행에서 옮긴 문서가 아직 옮겨 간 룸에 있으면 inbox로 돌아가고 다시 자동으로 옮기지 않는다. 그 실행이 만든 룸이 비면 지운다.

5. 구조와 실행

rooms-collect새 문서를 inbox에 링크, linked.jsonl에 기록
앱 (Tauri)roomsd가 뜬 뒤 1분마다 rooms-sort run. 키가 있으면 env로 넘김
rooms-sort대상 고르기 → R1~R5 → roomsd API로 이동/룸 생성 → 기록
roomsd이동과 룸 생성을 평소처럼 처리. 분류기를 모름

크레이트 crates/rooms-sort: rules.rs(순수 규칙), jev.rs(호출), api.rs(roomsd), doc.rs(repo 판단, 텍스트 추출), store.rs(SQLite), run.rs, main.rs. 의존: rooms-protocol, rooms-core(slug 규칙 room_slug/slug_key만, collect와 같은 비교를 위해), rusqlite, ureq, serde_json, toml.

한 번의 실행

  1. <data>/sort.lock 비차단 잠금. 이미 돌면 끝.
  2. GET /v1/rooms/inbox/artifacts. 대상(T1~T3)이 없으면 끝. 평소 대부분 여기서 끝난다.
  3. GET /v1/rooms, 룸마다 제목 5개를 위해 GET /v1/rooms/{id}/artifacts(Jev가 필요할 때만).
  4. 문서마다 R1, R2. 남은 문서는 키가 있으면 Jev(동시 4개, 실행당 최대 50개), 없으면 R5 no_key.
  5. 결정을 순서대로 적용: 이동은 POST /v1/artifacts/move, 룸 생성은 POST /v1/rooms. 이동 직전에 아직 inbox에 있는지 다시 확인.
  6. 결정과 실행 요약을 DB와 <data>/sort-status.json에 쓴다.

CLI

rooms-sort run [--dry-run]   # dry-run: 묻고 결정만 출력, 옮기지 않음
rooms-sort undo [--run ID]   # 기본: 마지막 실행
rooms-sort log [-n 20]       # 최근 결정과 이유(규칙 id, confidence)
rooms-sort check-key         # 키 확인: TypeSafe가 받으면 0, 거절하면 3

6. 저장소와 설정

데이터 폴더는 collect와 같은 곳(ROOMS_SORT_DATA로 바꿀 수 있음)에 sort.db를 따로 둔다.

decisions(file_key PK, title, repo, run_id, at, rule, action, why,
          to_room_id, choice, confidence, top_probs_json, model, rooms_hash)
repo_rooms(repo_key PK, room_id, created_at, forgotten INTEGER)
votes(repo_key, file_key, PRIMARY KEY(repo_key, file_key))
moves(run_id, file_key, artifact_id_after, from_room, to_room, created_room)
runs(run_id PK, started_at, ended_at, considered, moved, kept, rooms_created, input_tokens, error)

<home>/.rooms/sort.toml(없으면 기본값, 깨졌으면 무시하고 경고). 키는 이 파일에 절대 쓰지 않는다.

enabled = true            # false면 R1, R2도 멈춤
min_confidence = 0.7
new_room_min_docs = 3
model = "jev-1.13.0"

ignore_names = []         # N2 목록에 더함

7. API 키

규칙내용
K1앱에서 받은 키는 macOS 키체인에 저장한다(service computer.alto.rooms, account typesafe-api-key).
K2앱 프로세스에 비어 있지 않은 TYPESAFE_API_KEY가 있으면 그게 우선이고 "환경변수 사용 중"으로 보인다. Zed와 같은 규칙.
K3rooms-sort는 키체인을 읽지 않는다. 앱이 실행할 때 env로 넘긴다. 터미널에서는 같은 이름(TypeSafe SDK 표준)을 쓰면 된다.
K4저장할 때 검증 호출 1번. 200이면 저장, 401이면 저장하지 않는다.
K5"키 지우기"는 키체인 항목만 지운다. 기록은 남는다.

셸 env만 받는 방식은 쓰지 않는다. Finder나 Dock에서 띄운 앱은 셸 설정을 읽지 않는다.

8. 앱 연결

  • src-tauri/src/sorter.rs: roomsd가 응답한 뒤 시작 시 1번 + 60초 간격으로 rooms-sort run을 sidecar로 실행. 이전 실행이 안 끝났으면 건너뛴다. env: ROOMS_HOME, ROOMS_API_PORT, ROOMS_SORT_DATA, 키가 있으면 TYPESAFE_API_KEY.
  • src-tauri/src/sort_key.rs: Tauri 명령 sort_state(키 출처 none/keychain/env + sort-status.json), sort_set_key(검증 후 저장, 바로 한 번 실행), sort_clear_key, sort_undo_last.
  • 프런트: views/SortCard.tsx를 inbox 룸 위에.
  • 번들: externalBin과 build-sidecar.sh에 rooms-sort.

9. collect 변경

  • L8을 "언제나 <home>/inbox"로 바꾼다. 이름 일치는 rooms-sort R1이 맡는다.
  • linked.jsonl 형식은 그대로(rooms-sort가 T1에 쓴다). 이제 rooms-sort도 읽는 계약이므로 형식 변경은 양쪽 스펙에 적는다.
  • 사용자에게 보이는 차이: 이름 일치 문서가 inbox에 최대 1분 머문 뒤 룸으로 간다(T3 60초 + 실행 주기).

10. 스킬 v9

  • 첫 정리 7단계 안내문: "앞으로 앱이 열려 있으면 새 HTML은 inbox로 들어오고, 자동 분류가 repo 이름 룸으로 옮겨요. 키를 넣으면 다른 룸으로도 옮겨요. 주제별로 정리하고 싶으면 언제든 저에게 inbox 정리를 부탁하세요."
  • "Sorting the inbox" 첫 문단을 같은 내용으로 고친다. 정리 방법(제안 표 → 승인 → 링크 이동)은 그대로.
  • 버전 표시 rooms-onboarding v9.

11. 장애와 안전장치

  • roomsd가 응답하지 않으면 아무것도 하지 않고 끝난다.
  • 이동 직전 문서가 아직 inbox에 있는지 확인한다. 사용자가 그 사이 옮겼으면 건너뛰고 결정만 남긴다.
  • 본문은 데이터로만 쓴다. 문서 안의 지시문은 Jev가 보기 밖 값을 낼 수 없으므로 결과를 바꿀 수 있는 범위가 보기 선택뿐이다.
  • 오류는 stderr, runs.error, 상태 파일에 남는다. 401이 나면 앱은 키가 바뀔 때까지 Jev 단계를 멈추고 R1, R2만 돌린다.

12. 테스트

  • 규칙: R1~R5 각각, 순서(R1이 R3보다 먼저), N1~N5, 키 없음.
  • 입력: state 크기 상한, 홈 경로가 안 들어가는지, 보기 6,000자 상한과 none 포함.
  • 통합: 임시 home으로 roomsd를 띄우고 Jev는 가짜 HTTP 서버로. 이동이 createdAt을 지키는지, undo, 사용자가 옮긴 문서와 inbox에 직접 넣은 문서를 건드리지 않는지, 룸 이름을 바꿔도 R2가 맞는지.
  • collect: 같은 이름 룸이 있어도 inbox에 링크되는지(기존 테스트 수정).
  • 실제 키로 --dry-run을 사용자 inbox에 돌려 confidence 분포를 보고 기본 기준값을 정한다.

13. 열린 질문

  • 기준값 0.7로 정했다(사용자). dry-run에서 잘못 옮겨지는 문서가 많으면 올린다.
  • 본문 2,000자 정확도가 부족하면 늘린다. 비용은 거의 그대로다.

14. 구현 메모

스펙과 다르게 구현했거나 구현하면서 정한 것.

항목내용
화면 문구앱이 영어라 inbox 위 카드도 영어다("Sort the inbox automatically", "Auto-sort is on · 5 moved today, 2 left here").
undoroomsd는 inbox로 옮기는 이동을 거부한다(cannot move into inbox). 그래서 undo는 링크 자체를 inbox로 rename한다. fileKey는 원본 경로로 정해지므로 그대로이고, 결정이 undone으로 남아 다시 옮기지 않는다. 되돌린 문서의 createdAt은 되돌린 시각이 된다.
키 확인앱은 네트워크 코드를 늘리지 않고 rooms-sort check-key로 확인한다. TypeSafe와 통신하는 코드는 jev.rs 하나뿐이다.
거절된 키앱은 실행마다 TYPESAFE_API_KEY를 명시적으로 넘긴다. 키가 없거나 거절된 키면 빈 값을 넘겨서, 앱 환경의 키가 그대로 상속되지 않게 한다.
macOS 밖키체인이 없으므로 TYPESAFE_API_KEY만 쓴다. 키 저장은 안내 문구와 함께 실패한다.
T3 시각inbox에 들어온 시각은 Artifact의 createdAt이 아니라 linked.jsonl의 at(collect가 링크한 시각)을 쓴다.
본문 발췌script, style, noscript, template, svg, title 안의 텍스트는 뺀다(제목은 따로 들어가므로).
테스트 훅TYPESAFE_URL로 Jev 주소를 바꿀 수 있다(가짜 서버용).
스킬 v9안내문 두 곳을 고치고, 스킬이 inbox에 둔 링크는 자동 분류가 건드리지 않는다는 점을 적었다. 버전이 올라가서 기존 사용자에게도 다시 설치된다.
검증rooms-sort 테스트 24개(규칙별 단위 + 가짜 roomsd/Jev로 실행 전체), collect 테스트 수정, 앱 프런트 482개, 앱 Rust 테스트 통과. 실제 roomsd와 가짜 Jev 서버로 R1, R3, R4(룸 생성), R5, 거절된 키, dry-run, undo를 끝까지 돌려 봤다. 실제 TypeSafe 호출과 macOS 빌드는 아직 안 했다.
