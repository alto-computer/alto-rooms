rooms-sort — inbox를 비우는 분류기

Spec · 2026-10-09author: jun-hash선행: rooms-collect-spec, v1-spec (artifacts/move)모델: TypeSafe Jev

rooms-collect가 자동으로 모은 문서가 inbox에 쌓인다. rooms-sort는 사용자가 TypeSafe API 키를 한 번 넣으면 inbox 문서를 기존 룸으로 옮기는 별도 CLI다. 모델은 보기 중 하나를 고르기만 하고, 옮기는 일은 확신이 높을 때 결정적인 코드가 한다.

0. 개요

바뀐 결정 (사용자): rooms-collect 스펙 §0은 "Rooms는 AI를 부르지 않는다, 분류는 스킬의 일"이었다. 수집이 자동이 되면서 inbox가 쌓이므로, artifact 싱크·분류·관리를 Rooms의 역할로 보고 사용자가 키를 넣었을 때만 분류를 켠다. 코어(roomsd)와 rooms-collect는 여전히 AI를 모른다.

결합: rooms-sort는 roomsd의 이미 있는 공개 API(rooms-mcp가 쓰는 것과 같은 것)와 ~/rooms 폴더, sources.json만 읽는다. 새 API, collect 코드 변경은 없다.

Goal

  • 키를 넣은 뒤로 inbox에 들어온 문서 중 확신 높은 것은 몇 분 안에 맞는 룸으로 옮겨진다.
  • 애매한 문서는 inbox에 남는다. 틀린 이동보다 안 옮기는 쪽을 택한다.
  • 룸이 없는 같은 git repo에서 온 문서가 3개 이상 inbox에 쌓이면 그 repo 이름으로 룸을 만들어 옮긴다(§6).
  • 모든 이동은 기록되고 되돌릴 수 있다. 사용자가 손댄 문서는 다시 건드리지 않는다.
  • 상주 메모리 0. 앱이 필요할 때만 실행하고 끝난다.

Out of scope

  • 주제로 새 룸 이름 짓기(예: "디자인 리서치"). Jev는 고르기만 한다. 사람이나 온보딩 스킬이 만든다.
  • inbox 밖 문서 재분류, 룸 간 이동, 룸 병합.
  • TypeSafe 외 제공자, 로컬 모델. 호출부를 한 함수로 가둬 나중에 붙일 수 있게만 한다.
  • 앱 안 분류 기록 화면. 이번에는 설정의 상태 한 줄과 "마지막 분류 되돌리기" 버튼까지.

1. 사용자 경험

처음 한 번

  1. 설정 → 자동 분류. "키 받기"를 누르면 console.typesafe.ai/keys가 열린다.
  2. 키를 붙여 넣고 저장. 앱이 작은 테스트 호출로 확인하고 "연결됨"을 보여준다. 401이면 "키가 맞지 않아요. 콘솔에서 다시 복사해 주세요."
  3. 설명 한 줄: "inbox 문서의 제목과 본문 앞부분이 TypeSafe로 보내져요. 확신이 높을 때만 옮기고, 언제든 되돌릴 수 있어요."

평소

사용자는 아무것도 하지 않는다. 문서가 inbox에 잠깐 보였다가 룸으로 옮겨진다. 설정에는 "오늘 12개 분류, 3개는 inbox에 남김 · 2분 전" 같은 상태 한 줄이 있다.

되돌리기

설정의 "마지막 분류 되돌리기" 또는 rooms-sort undo. 그 실행에서 옮긴 문서가 아직 옮겨 간 룸에 있으면 inbox로 돌아가고, 다시는 자동으로 옮기지 않는다. 그 실행이 만든 룸이 비면 지운다.

2. 결정

항목결정이유
위치collect 밖, 별도 바이너리 rooms-sortcollect는 모든 에이전트 로그를 읽는 오프라인 프로세스다. 네트워크와 키를 넣으면 로그 전체가 외부로 나갈 수 있는 프로세스가 된다. 밖에 두면 분류기는 inbox 문서만 본다. API 장애가 수집에 번지지 않고, collect에 TLS 스택이 안 들어간다.
모델TypeSafe Jev, Choice 질문생성하지 않고 보기 중 하나와 확률, confidence를 돌려준다. 잘못된 룸 이름이나 JSON 파싱 실패가 없다. 출력 무료, 입력 $0.042/1M 토큰, 70~500ms.
이동 기준confidence ≥ 0.85면 이동, 아니면 inbox에 둠사용자 선택("확신 높으면 이동"). 기준값은 설정 가능.
실행 방식일회성 CLI. 앱이 5분마다, 그리고 시작할 때 실행상주 메모리 0. 할 일이 없으면 API 한 번 묻고 바로 끝난다.
이동 방법roomsd POST /v1/artifacts/move코어의 이동은 createdAt과 Journal 날짜를 지킨다. 폴더에서 직접 rename하면 새 문서처럼 보인다.
룸 만들기roomsd POST /v1/rooms같은 이유. 코어가 룸을 기록하고 이벤트를 낸다.
키 저장macOS 키체인, TYPESAFE_API_KEY env 우선§8. Zed와 같은 규칙.

3. 구조

rooms-collect문서를 inbox에 링크하고 출처를 sources.json에 적는다.
앱 (Tauri)키가 있으면 5분마다 rooms-sort run을 실행. 키는 env로 넘긴다.
rooms-sortroomsd API로 룸과 inbox를 읽고, Jev에 묻고, 옮긴다.
roomsd이동과 룸 생성을 평소처럼 처리. 분류기를 모른다.

크레이트: crates/rooms-sort. 의존: rooms-protocol(Artifact, Room 타입, 기본 포트), rusqlite, ureq(rustls, 동기 HTTP. tokio 없이 작게), serde_json, toml. rooms-core에는 의존하지 않는다.

환경변수는 rooms-mcp와 같은 이름을 쓴다: ROOMS_HOME(기본 ~/rooms), ROOMS_API_PORT(기본 4317), 토큰은 <home>/.rooms/token. 여기에 TYPESAFE_API_KEY.

4. 한 번의 실행

단계하는 일
R1잠금 <data>/sort.lock을 비차단으로 잡는다. 이미 돌고 있으면 바로 끝난다.
R2키가 없거나 sort.toml의 enabled = false면 끝난다.
R3GET /v1/rooms/inbox/artifacts. DB에 결정이 있는 file_key는 뺀다. 남은 게 없으면 끝난다(평소 대부분 여기서 끝남).
R4방금 들어온 문서는 기다린다: created_at이 60초 안이면 다음 실행으로 미룬다(에이전트가 아직 쓰는 중일 수 있음).
R5GET /v1/rooms로 보기를 만든다: owned 룸 중 inbox, journal 제외. 각 룸의 설명은 이름 + 최근 문서 제목 최대 8개(§5).
R6문서마다 state를 만든다: 제목, 원본 경로, repo 이름(sources.json의 cwd와 경로로 판단), 본문 앞 12KB의 보이는 텍스트(script/style 제거).
R7문서마다 Jev 호출, 동시 4개, 한 실행에 최대 50개.
R8결과 처리: 기존 룸이 뽑히고 confidence ≥ 기준이면 이동. "맞는 룸 없음"이 뽑히거나 기준 미만이면 inbox에 두고, repo가 있으면 그 repo 후보에 표를 준다(§6).
R9표가 3개 이상 모인 후보는 룸을 만들고 그 문서들을 옮긴다.
R10모든 결정을 DB에 적고 <data>/sort-status.json에 요약을 쓴다(앱 상태 줄용).

한 번 결정한 문서는 다시 묻지 않는다. 남겨 둔 문서도 마찬가지다. 단, 룸 목록이 바뀌면(새 룸이 생기거나 이름이 바뀌면) 남겨 둔 문서를 한 번 더 묻는다.

5. Jev 호출

POST https://api.typesafe.ai/v1/systemone
Authorization: Bearer $TYPESAFE_API_KEY

{
  "model": "jev-1.13.0",
  "state": "제목: Canvas 렌더 성능 메모\n경로: ~/code/rooms-plugin-excalidraw/notes/canvas-perf.html\nrepo: rooms-plugin-excalidraw\n\n본문: ...",
  "questions": {
    "room": {
      "type": "choice",
      "instructions": "이 문서를 어느 룸에 두면 사용자가 나중에 찾기 쉬운가?",
      "criteria": {
        "r_9f2c": "alto-rooms — 포함: rooms-collect 스펙; v2 ask 스펙; 플러그인 도구 스펙",
        "r_41aa": "디자인 리서치 — 포함: 경쟁사 온보딩 분석; 컬러 시스템 비교",
        "none":   "위 어느 룸에도 뚜렷이 맞지 않음"
      }
    }
  }
}
  • 보기 키는 룸 id. 이름이 바뀌어도 결정과 연결이 유지된다. Choice는 최대 255개라 룸이 254개를 넘으면 최근 활동순 254개만 넣는다.
  • 모델은 버전을 고정한다(jev-latest는 쓰지 않음). 바꿀 땐 sort.toml의 model.
  • 응답의 choice, confidence, probabilities를 그대로 DB에 남긴다. 기준값을 나중에 조정할 근거가 된다.
  • 429, 529는 지수 백오프로 최대 3번. 401은 실행을 멈추고 상태에 "키 오류"를 적는다.

6. 새 룸 규칙

새 룸 이름은 모델이 짓지 않고 문서 출처에서 가져온다.

규칙내용
N1후보 이름은 문서의 repo 이름(collect의 repo_info와 같은 규칙, worktree는 본 repo 이름). repo가 없으면 후보 없음.
N2일반 폴더 이름은 후보가 아니다: Downloads, Desktop, Documents, tmp, docs, notes, out, dist, build, scratch, untitled. 목록은 sort.toml에서 늘릴 수 있다.
N3문서가 기존 룸으로 옮겨지지 않았고 후보가 있으면 그 후보에 표 1개.
N4한 후보의 표가 3개(new_room_min_docs)가 되면 그 이름으로 룸을 만들고 표를 준 문서를 모두 옮긴다.
N5만든 룸은 repo_rooms(repo_key → room_id)에 기억한다. 사용자가 이름을 바꿔도 같은 repo 문서는 그 룸으로 간다. 룸이 지워졌으면 연결을 지우고, 다시 만들지 않는다(사용자가 지운 것으로 본다).
N6사용자가 룸 이름을 repo 이름과 같게 만들면 collect가 처음부터 그 룸에 넣으므로 분류기는 개입하지 않는다.

예시

기존 룸 alto-rooms, 디자인 리서치. 하루 동안:

  1. ~/code/alto-rooms/docs/sort-spec.html: collect가 바로 alto-rooms에 넣는다. 분류기는 보지 않는다.
  2. ~/code/rooms-plugin-excalidraw/notes/의 HTML 3개: Jev가 "none"을 고르고 후보 rooms-plugin-excalidraw에 표가 쌓인다. 세 번째에 룸이 생기고 셋이 옮겨진다.
  3. ~/Downloads/competitor-onboarding-teardown.html: 후보 없음(N2). Jev가 디자인 리서치를 0.86으로 고르면 옮긴다.
  4. /tmp/claude-…/report.html: 후보 없음, 기준 미만. inbox에 남는다.

7. 저장소와 설정

데이터 폴더는 collect와 같은 곳(~/Library/Application Support/computer.alto.rooms, ROOMS_SORT_DATA로 바꿀 수 있음)에 sort.db를 따로 둔다. collect의 DB는 읽지 않는다.

decisions(file_key PK, artifact_id, title, repo_key, run_id, at,
          choice, confidence, probabilities_json, model,
          action TEXT CHECK(action IN ('moved','kept','voted','created','undone')),
          to_room_id, rooms_hash)
repo_rooms(repo_key PK, room_id, created_at)
votes(repo_key, file_key, PRIMARY KEY(repo_key, file_key))
runs(run_id PK, started_at, ended_at, asked, moved, kept, created_rooms, error)

rooms_hash는 그때 보기로 쓴 룸 id 목록의 해시. 룸 목록이 바뀌면 kept 문서를 다시 묻는 데 쓴다.

<home>/.rooms/sort.toml(없으면 기본값, 깨졌으면 무시하고 경고):

enabled = true
min_confidence = 0.85
new_room_min_docs = 3
model = "jev-1.13.0"
max_docs_per_run = 50
max_state_bytes = 12288
ignore_folder_names = []   # N2 목록에 더함

키는 이 파일에 절대 쓰지 않는다.

8. API 키

규칙내용
K1앱 설정에서 받은 키는 macOS 키체인에 저장한다. service computer.alto.rooms, account typesafe-api-key. 평문 파일에는 두지 않는다.
K2앱 프로세스에 비어 있지 않은 TYPESAFE_API_KEY가 있으면 그게 우선이고, 설정에 "환경변수 사용 중"이라고 보인다(입력칸 비활성).
K3분류기는 키체인을 읽지 않는다. 앱이 꺼내서 실행할 때 env로 넘긴다. 키체인 권한 팝업은 앱에서만 뜨고, CLI는 env만 아는 단순한 프로그램으로 남는다. 터미널에서 직접 돌릴 때도 같은 이름이 TypeSafe SDK 표준이다.
K4저장할 때 검증 호출 1번(보기 2개짜리 Choice). 200이면 저장, 401이면 저장하지 않고 안내.
K5"키 지우기"는 키체인 항목을 지운다. 이후 분류는 실행되지 않는다. 기록(DB)은 남는다.

셸 env만 받는 방식은 쓰지 않는다. Finder나 Dock에서 띄운 앱은 셸 설정을 읽지 않아서 "등록했는데 안 되는" 상태가 생긴다.

9. 앱 연결

  • apps/desktop/src-tauri/src/sorter.rs: collector.rs와 같은 구조. roomsd가 응답한 뒤, 키가 있으면 시작 시 1번 + 5분 간격으로 rooms-sort run을 sidecar로 실행. 실행 중이면 건너뛴다. env: ROOMS_HOME, ROOMS_API_PORT, TYPESAFE_API_KEY.
  • Tauri 명령: sort_key_status(없음/키체인/환경변수), sort_set_key(검증 후 저장), sort_clear_key, sort_status(sort-status.json 읽기), sort_undo_last(rooms-sort undo 실행).
  • 설정 화면에 "자동 분류" 섹션: 키 입력, 키 받기 링크, 연결 상태, 상태 한 줄, 되돌리기 버튼, 보내는 내용 설명.
  • 번들: externalBin에 rooms-sort 추가, 릴리스 스크립트에 빌드 추가.

CLI

rooms-sort run [--dry-run]   # dry-run: 묻기만 하고 옮기지 않고 계획을 출력
rooms-sort undo [--run ID]   # 기본: 마지막 실행
rooms-sort log [-n 20]       # 최근 결정과 confidence

10. 장애와 안전장치

  • roomsd가 응답하지 않으면 아무것도 하지 않고 끝난다.
  • 이동 직전 문서가 아직 inbox에 있는지 확인한다. 사용자가 그 사이 옮겼으면 kept로 적고 건드리지 않는다.
  • 사용자가 분류기가 옮긴 문서를 inbox로 되돌리면 file_key가 이미 DB에 있으므로 다시 옮기지 않는다.
  • 보내는 내용은 문서 제목, 경로, repo 이름, 본문 앞 12KB뿐. 에이전트 대화 로그는 읽지도 보내지도 않는다.
  • 한 실행 최대 50개 × 12KB. 일반적인 하루 사용 비용은 1센트 미만.
  • 오류는 stderr와 runs.error, 상태 파일에 남는다. 연속 401이면 앱이 다음 키 저장까지 실행을 멈춘다.

11. 테스트

  • 단위: state 만들기(텍스트 추출, 12KB 자르기), 보기 만들기(255개 제한, none 포함), 결과 처리(기준 이상/미만/none), 표와 룸 생성(N1~N6), 일반 폴더 제외.
  • 통합: 임시 home으로 roomsd를 띄우고 Jev는 가짜 HTTP 서버로 대신한다. 이동이 createdAt을 지키는지, undo가 되돌리는지, 사용자가 옮긴 문서를 건드리지 않는지, 룸 이름을 바꿔도 repo 연결이 유지되는지.
  • 앱: 키 상태 3가지, 검증 실패 시 저장 안 됨.
  • 실제 키로 --dry-run을 사용자 inbox에 돌려 confidence 분포를 보고 기본 기준값을 정한다.

12. 구현 순서

  1. crates/rooms-sort: roomsd 클라이언트, Jev 클라이언트, DB, run/undo/log, --dry-run.
  2. 새 룸 규칙과 repo 연결.
  3. 앱: 키체인, 설정 섹션, 주기 실행, 번들.
  4. 실제 inbox로 dry-run, 기준값 조정, 릴리스.

13. 열린 질문

  • 기준값 0.85는 출발점이다. TypeSafe 쿡북은 0.9를 썼다. dry-run 결과로 정한다.
  • 본문 범위 12KB면 대부분의 스펙 문서 앞부분이 들어간다. 더 줄여도 정확도가 유지되는지 dry-run으로 본다.
  • 컨텍스트 공개 자료마다 32k, 64k로 다르게 적혀 있다. 보기 설명과 본문을 합쳐 8k 토큰 안으로 유지해 어느 쪽이든 안전하게 한다.
